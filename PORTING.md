# Porting `jimbot_sim` to Rust

The Python simulator is the `jimbot-sim` repository
(`git@github.com:mmank/jimbot-sim.git`, package `src/jimbot_sim`); `rumbot`
carries it as the submodule `external/jimbot-sim`. This crate, `rumbot_sim`, is a
module-for-module translation of it. It was written inside `rumbot` as
`rust/jimbot_sim` and moved to this repository of its own on 2026-10-04, history
kept; paths below that start `rust/handcrafted/` or `scripts/` are in `rumbot`.

## Synced through the simulator's `cff6f88`

The port tracks the submodule pin, which is the simulator's `main` at
`cff6f88`. Three commits landed on that main after the first fixtures were
generated (`8c7f21e`), and exactly one touches the pure simulator:

| commit | what | ported? |
|---|---|---|
| `fa9f8e0` | **Joker Stencil counts the stencils, not just itself** (`jokers.py`) | **yes** — `joker_specs.rs::joker_stencil`, pinned by `tests/joker_stencil.rs` (the engine's four rows: 180/360/1440/7500) |
| `36924b0` | `was_won`: a run that dies at the final boss is not a win (`headless/driving.py`, `bot_api.lua`) | no — bridge/headless, not part of this port |
| `cff6f88` | press the win screen's Continue from inside the wait (`run.py`, `bridge/client.py`, `headless/driving.py`) | no — the engine driver, not the pure simulator |

The fix changes no existing fixture: a *single* Stencil reads the same either
way, and none of the recorded states holds two, which is why the whole fixture
set regenerated byte-identical against `cff6f88`. The new test is what pins it.

## Why the RNG is the whole ballgame

Balatro does not draw from one stream. Every decision names a pool (`"Joker1"`,
`"shop_pack"`, `"erratic"`) and each pool keeps its own state, so a simulator
drawing from a generic PRNG plays a *different game* on the same seed: every rule
looks right and every hand is wrong. `rng.rs` therefore reproduces LuaJIT's
`math.random` (TW223) and the game's `pseudohash`/`pseudoseed` bit-for-bit, and
`tests/rng_fixture.rs` replays 2,270 reference draws from the Python original and
compares **bits**, not printed digits. A port that is merely close passes no line
of that fixture, which is the point.

## The one architectural decision that cannot be avoided

Python's jokers are closures registered into a dict:

```python
@dataclass(frozen=True)
class JokerSpec:
    scored: ScoredHook | None = None      # (joker, card, ctx) -> None
    independent: IndepHook | None = None  # (joker, ctx) -> None
```

and `ScoreContext` holds a live `&mut GameState` (`ctx.game`), which the hooks
mutate freely -- a joker grows its counter, takes money, draws from the RNG. Rust
cannot lend the run out mutably while the same pipeline is passing the context
around, so the translation has to change the *shape* of the interface, not just
its syntax. The chosen shape, already applied in `effects.rs`:

1. **Inject what the context used to read off the run.** Python's
   `ScoreContext.money` is `max(0, game.money + money_gained)` and
   `ScoreContext.expect` needs `game.probability_scale()`. Both are constants for
   the duration of a hand -- the simulator banks `money_gained` only after
   scoring, so `game.money` does not move while any of this runs -- so they
   become `ScoreContext.base_money` and `ScoreContext.probability_scale`. This is
   exact, not approximate.

2. **Pass the run explicitly to the hooks that need it.** The hook signatures
   become, in `jokers.rs`:

   ```rust
   type ScoredHook  = fn(&mut JokerInstance, &Card, &mut ScoreContext, &mut GameState);
   type IndepHook   = fn(&mut JokerInstance, &mut ScoreContext, &mut GameState);
   type RoundHook   = fn(&mut JokerInstance, &mut GameState);
   ```

   i.e. `fn` pointers rather than `Box<dyn Fn>`, which keeps `JokerSpec` `const`
   and the registry a plain `&'static [JokerSpec]`. The registry is built with a
   `macro_rules!` `register!` or a `const` array, mirroring the Python
   `register(...)` calls one for one.

3. **Iterating the row while mutating it.** `scoring::effective_specs` walks
   `game.jokers` and calls a copied joker's own ability; in Rust the row must be
   indexed rather than borrowed. The portable trick is to take the row out
   (`std::mem::take(&mut game.jokers)`), walk it, and put it back -- the hooks
   then see the full row through `game` while the walk holds the instances in a
   local. `scoring.py`'s comment about a Blueprint adding the *dagger's*
   accumulated mult (not the copier's) is the reason the row cannot simply be
   copied: the hook must run against the copied joker's own counter.

4. **Copier resolution.** `spec.copier` (`"right"` / `"leftmost"`) resolves to a
   `(spec, source_index)` pair, exactly as `effective_specs` returns today. Keep
   that function's comments; they record three bugs that were found only by
   differential replay.

## How the differential tests work

Every module that can be checked is checked against the Python original by a
generated fixture, produced by a script under `tools/` that imports the Python
module and writes a text file:

```bash
cd /tmp/balatro_rust
/home/marcin/balatro_bot/.venv/bin/python tools/gen_rng_fixture.py \
    > tests/fixtures/rng_stream.txt
cargo test --offline
```

The float fields are emitted with `%.17g`, which round-trips a double exactly, so
the Rust side compares `to_bits()` rather than printed digits. This is the
standard the rest of the port should meet:

### A fixture that drops a key when it is empty cannot notice a missing key

This was found the hard way. The observation fixture flattened dicts and lists
and emitted a leaf only for scalars, so an empty list produced no leaf at all --
and four top-level keys (`jokers`, `consumables`, `shop`, `pack`) were empty in
every case and therefore compared by nothing. Those four are rendered by
`joker_row`, `consumable_row`, `shop_row` and `pack_row`, the most intricate
functions in `state.rs`, and they were unverified while the test was green.

The fix has two halves, and both are needed: emit a leaf for an empty container so
its *presence* is asserted, and add cases that populate the rows. The test now
asserts the number of distinct top-level keys compared equals the number
`state_dict` actually returns (42), so a key added on one side and not the other
fails the build rather than quietly going untested. **When you add a differential
fixture, assert the key or case count against the Python rather than a floor.**

### A key that is compared but never varied cannot catch a bug

The same lesson one level up from a single key's *presence*: counting the
distinct digest each top-level key takes across all 4,140 replay steps shows 34
vary and 8 never do. A key whose value is the same at every step is compared at
every step but exercises nothing, so a wrong formula for it passes. The eight
were closed as follows:

  * **Literals by construction, pinned on purpose** -- `in_run` (state.py:471),
    `highlight_limit` (499), `sorted_rank` (504) and `sorted_suit` (505) are
    set as literals, not read off the game; a constant digest is the *correct*
    treatment, and the fixture header names them so nobody "fixes" them.
  * **Caller parameters, not derived** -- `toggles_used` and
    `joker_swaps_used` are `state_dict` arguments (the replay driver passed 0
    every step). They are now varied per step (`step % 6` and `step*3 % 7`),
    emitted as their own columns, handed identically to both engines, and the
    test asserts the fixture carries all 6 and 7 distinct digests.
  * **`won`** is 0 in every recording only because no recorded run was won; a
    synthetic `state.txt` case sets the phase to WON and pins `won=1` with
    `state_name=GAME_OVER`.
  * **`bankrupt_at`** is a real gap: it is 0 unless Credit Card is held, and
    Credit Card was offered 38 times but held in 0 steps, so `bankrupt_at`,
    `spendable` and `affords` -- its entire mechanic -- were unexercised.
    Synthetic cases hold one and two cards (`bankrupt_at` -20 and -40), and a
    Rust test pins the exact numbers `game.py`'s docstring specifies: at $0 one
    allows $20 and refuses $21, two allow $40 and refuse $41, and `affords(0)`
    is true past the floor.

The remaining keys with fewer than five distinct values (`boss`, `skippable`,
`consumable_limit`, `joker_limit`, `deck`, `stake`, `ancient_suit`,
`idol_suit`, `castle_suit`) are genuine: they are binary flags, the four suits,
the four decks and four stakes the recordings happen to use, or slot counts
only a voucher or a Negative moves.

For the remaining modules the fixture should be *end-to-end*: drive a whole run
in both engines with the same seed and compare the state after every step --
hand contents, `chips_scored`, money, shop slots, RNG pool state. `game.py`
contains the recorded divergences that got the Python simulator to zero; each
one is a test case the Rust port must pass, so the fixtures are best built from
the recordings in `external/jimbot-sim/recordings/` and from the seed lists in
`ops/`.

## Deliberate differences from the Python

* Log strings in `effects.rs` use Rust float formatting where Python used `%g`.
  No test compares logs.
* `Card`'s `uid` counter is thread-local rather than process-global. Python's
  `itertools.count()` is process-global under the GIL; a per-thread counter keeps
  two Rust tests from interleaving ids and shuffling each other's decks. Within a
  thread the order is exactly the game's.
* The `hands::evaluate` memoisation cache (`_SHAPES`) is not ported. It is a
  pure optimisation: the cache key is the shape plus the four flags, and the
  answer is a pure function of them, which is precisely why dropping it cannot
  change a result.
* Face-down cards (see "Face-down cards" below). The Python never turned a
  card over, so it never rolled The Wheel's `wheel` pool; the Rust does, and
  the Python-recorded fixtures leave that one pool out of their comparison
  (`rng::LUA_ONLY_POOLS`). Amber Acorn also shuffles its row beside Chicot,
  which the Python skipped.
* Erosion counts the cards below `GameState::starting_deck_size`, the full
  deck as the run dealt it (`G.GAME.starting_deck_size`, game.lua:2375), where
  the Python counts below a flat 52. The two agree on every deck but the
  Abandoned, whose 40 cards the Python paid +48 Mult for. No fixture plays
  Erosion on an Abandoned Deck; the live game found it (DM46XNV1, stake 8).

## Speed: Rust against CPython and PyPy

`cargo run --release --bin sim_bench` and `tools/bench_python.py` measure the same
three workloads with the same seeds and the same policy, so the comparison is work
for work rather than a rule of thumb. One chip a blind and endless play keep the
runs moving; both stop at ante 12, because past ante 15 Python's `ante_base_chips`
overflows to infinity and raises where the Rust port saturates its `i64` cast.

On an Intel i7-8700, single-threaded, 608 steps / 8 runs and 3,421 previews and
4,000 `legal_actions` calls in each language:

| workload | CPython 3.12 | PyPy 7.3.23 | Rust (release) | Rust vs CPython | Rust vs PyPy |
|---|---|---|---|---|---|
| whole-run rollout | 241 steps/s | 304 steps/s | ~5,800 steps/s | **24x** | **19x** |
| `preview_score` | 9,349 /s | 19,153 /s | ~158,000 /s | **17x** | **8.3x** |
| `legal_actions` | 1,725 /s | 13,837 /s | ~25,000 /s | **14.5x** | **1.8x** |

The shape of these matters more than the headline. The rollout is
preview-dominated -- a step scores ~400 candidate plays before it moves -- and
**PyPy is 8x faster than CPython on `legal_actions` but only 2x on
`preview_score`**, so PyPy's advantage largely evaporates on the workload that
dominates. That is why PyPy's rollout is only 1.3x CPython's while Rust's is 24x.

Caveats worth keeping: these are single-threaded on one machine; the Rust is
release with LTO; and the Python figures exclude the harness around the simulator
(observation encoding, action masking), which is more Python cost the Rust would
absorb -- so a real training step would favour Rust by more, not less.

### The 1-chip fuzz differential

Every blind's target is forced to **1 chip**, so any play beats the blind, and the
actions are chosen **uniformly at random** from `legal_actions()`. Runs then
progress deep and fast while reaching states no scripted policy and no human
recording did -- ante 11 here, past both.

Per step it compares the chosen action, a digest of **every legal action** (in
`legal_actions()` order and sorted), all 42 observation-key digests, and the RNG
pool signature. The legal-action digests are the valuable part: `legal_actions()`
is the entire interface to the rules, so a digest over it validates the whole
action mask -- which no other fixture here does. 1,547 steps gave 3,094
legal-action digests and 64,974 key digests.

The sweep is the same harness at 60x the scale, made affordable by a **rolling
digest per seed**: FNV-1a-64 is incremental, so folding each step's canonical
bytes one at a time equals hashing the run at once, and the fixture is one line
per seed plus a checkpoint every 25 steps to localise a mismatch. It also removed
the need to emit actions at all -- the chooser is the simulator's own `RunRng`
under a per-seed pool name, which `rng.rs` already reproduces bit for bit, so both
engines pick the same action without it being written down.

**640 seeds, 119,936 steps, 5,017 checkpoint comparisons, deepest ante 15, no
divergence.** The assertion compares the replay's totals to the fixture's own
declared totals exactly; a floor was tried first and it lied (`MIN_STEPS = 100_000`
failed against a consistent 95,437-step fixture), which is the same lesson as the
empty-container and dead-branch fixtures above.

It found the `dollar_rows` bug (below) and, at ante 16+, the `i64` ceiling in
`ante_base_chips`: Python's integers are unbounded and `state_dict`'s `blinds` row
reports that unbounded value, so the *observation* diverges past ante 15 in
endless play. That is recorded, not papered over -- closing it needs
arbitrary-precision integers throughout (a `chips_scored` of `i64` has the same
ceiling), and the fuzz fixture is capped below it.

## The frozen interface (built, committed, do not re-litigate)

### Shared handles

`Card`, `JokerInstance` and `ConsumableInstance` are values behind a shared
handle, because Python's are objects and the run holds the *same* object in
several lists:

```rust
pub type CardRef  = Rc<RefCell<Card>>;
pub type JokerRef = Rc<RefCell<JokerInstance>>;
pub type ConsumableRef = Rc<RefCell<ConsumableInstance>>;
```

This is not a convenience. `GameState::remove_card` walks `full_deck`,
`draw_pile`, `hand` and `discard_pile` and removes the card from *each*, and
`add_card` puts one object into two of them; with value semantics the piles
diverge on the first enhancement and every later deal is from a different deck.
Identity is the `uid`, so `PartialEq`/`Hash` are by uid -- Python's `eq=False`.

A `Card` field and a method of the same name coexist (`self.original_suit` reads
the stored override, `self.original_suit()` the effective suit); Rust keeps the
two namespaces apart, which is why the Python property maps over unchanged.
Free accessors (`uid_of`, `make_card`, `copy_card`, `rank_of`, ...) keep call
sites readable without `borrow()` noise.

### Hooks

```rust
pub type ScoredHook    = fn(&JokerRef, &CardRef, &mut ScoreContext, &mut GameState);
pub type IndepHook     = fn(&JokerRef, &mut ScoreContext, &mut GameState);
pub type RoundHook     = fn(&JokerRef, &mut GameState);
pub type DiscardHook   = fn(&JokerRef, &[CardRef], &mut GameState);
pub type RetriggerHook = fn(&JokerRef, &CardRef, &mut ScoreContext, &mut GameState) -> i32;
pub type OtherJokerHook = fn(&JokerRef, &JokerRef, &mut ScoreContext, &mut GameState);
```

Because the instance lives behind the `Rc`, `&mut GameState` and the joker handle
are borrowed at the same time without any aliasing -- so `hook(joker, self)`
becomes `hook(&joker, game)` one for one, and the row can be walked while hooks
mutate the run.

`ScoreContext` no longer holds the run. `base_money` and `probability_scale` are
injected; both are constant for the duration of a hand, so the substitution is
exact (see `effects.rs`).

Specs are `const`-constructible so the registry is a `&'static [JokerSpec]`
spread from `..JokerSpec::DEFAULT`. Lookup is a lazily built index, and
`spec_or_panic` panics with the name rather than returning nothing -- a missing
spec must never be mistaken for a joker that does nothing.

### What Python's deferred closures became

`blind_select_events` is a list of closures in Python, each capturing the run.
Rust closures cannot capture the run they are stored inside, so the queue holds
data and the pass performs it:

```rust
pub enum BlindSelectEvent {
    CreateJokers { source_uid: u64, count: i32 },
    DestroyJoker { victim_uid: u64, reason: String },
}
```
Same order, same effect: the pass finishes, then the events run, then the sliced
jokers go.

### Where GameState's methods live

`game.rs` holds the struct, the constructor, the accessors and the vocabulary.
The mutation methods are split into further `impl GameState` blocks so that two

### Seed-faithful

`GameState::new` now performs the Python `__post_init__` in full -- the boss, the
round voucher and the two ante tags are rolled before anything else, so the run's
pool state matches the Python original from the first step. `tests/flow_fixture.rs`
replays a deterministic policy against the Python simulator -- one that plays the
blinds, buys jokers and consumables, rerolls, opens boosters and uses tarots, so
the shop, pack and consumable paths are all walked -- and matched **2,166 steps
across 32 seeds**, deepest ante 5, with no disagreement. The per-step record
compares the phase, ante, action, money, hands, discards, hand, joker row,
consumable row, whole shop row, an open booster's options, chips and the raw RNG
pool state. That shop/pack comparison is what caught the `RunRng::seeded` bug:
`live` was stored as a clone taken *before* the draw, so a bare `math.random`
(the first shop's Buffoon pack) read one draw behind the game.

And the RNG fixture **did not catch it**, which is its own lesson: its `live`
records made a bare draw after a `seeded` call but never a *named* draw in
between, so `live` was never asked to advance through one. The `livemix` records
(`tools/gen_rng_fixture.py`) now interleave a named draw with a bare one, and
reintroducing the bug fails them on the first record with both values printed.
A fixture only tests the sequences it actually performs -- the same lesson as the
empty-container one above.

### Face-down cards

Four bosses deal cards face down and a fifth turns the joker row over. None
of it changes a rule -- a face-down card scores as itself -- so the port first
left all five blank, "since this engine has full information anyway". That was
true of the engine and not of the policy playing it, which read every
face-down card: 49 of the 58 wins on 10,000 gold-stake runs met one of them.
They are now marked, on the cards themselves, the way the game marks them:

```rust
pub struct Card          { /* ... */ pub face_down: bool }
pub struct JokerInstance { /* ... */ pub face_down: bool }
pub struct BossEffect    { /* ... */
    pub face_down_first_hand: bool,  // The House
    pub face_down_odds: i32,         // The Wheel: 7
    pub face_down_faces: bool,       // The Mark
    pub face_down_after_play: bool,  // The Fish
    pub shuffles_jokers: bool,       // Amber Acorn, which also turns the row over
}
```

`GameState::_stay_flipped` is `Blind:stay_flipped` (blind.lua:605), asked of
every card dealt into the hand, one at a time in deal order, by both draw
loops (`_draw_to_hand_size`, `_draw_cards` -- so The Serpent's three, a Juggler
card and The Manacle's return are asked too). A pack's deal happens with no
blind in force and is never asked.

| boss | a card is dealt face down when | the rule's state |
|---|---|---|
| The House | no hand played and no discard used this round | `hands_played_this_round`, `discards_used` |
| The Wheel | `pseudorandom(pseudoseed('wheel')) < normal/7` | its own `wheel` pool, one draw a card dealt while it is live |
| The Mark | `is_face(true)`: J, Q, K, and *every* card beside Pareidolia | `jokers::is_face_for(card, game, true)` |
| The Fish | `Blind.prepped`: cleared by set_blind for the Fish, set by each press_play, cleared by drawn_to_hand | `Blind.prepped`, already there for Crimson Heart |
| Amber Acorn | every joker in the row as the blind is set, before any joker hears setting_blind | turned over in `_start_round` |

Turned face up again: a card as it is played (the emplace into `G.play`,
cardarea.lua:38) or discarded; the hand and the row by `Blind:disable`
(`disable_blind` -- Chicot at set_blind, Luchador mid-round) and at the end of
the round (`Blind:defeat`). A copy (`Card::copy`, `copy_joker`) is a new card,
made face up. Nothing in `state_dict` reads the flags, so the observation, and
every fixture digest of it, is unchanged. Beside Chicot the boss is disabled
before the deal: nothing is face down and the Wheel never rolls -- but Amber
Acorn still shuffles, because set_blind queues the shuffle before Chicot's
setting_blind queues the disable; it just leaves the row face up. The port had
skipped that shuffle too.

The Python fixtures cannot check any of this, and they need one allowance:
the first time the Wheel rolls, a `wheel` key appears in the pool map they
compare after every step. No other pool moves -- that is what naming the pools
buys -- so they compare the map less `rng::LUA_ONLY_POOLS` and match to the
bit as before. What pins the rule is `tests/facedown_fixture.rs`, the first
fixture here **recorded off the game's own Lua** rather than the Python:
`scripts/gen_facedown_fixture.py` boots the real game headless
(`HeadlessBalatro`, from the submodule, over `vendor/balatro_src`), puts each
boss on the opening blind of 15 seeds across the decks, plays a fixed script
of discards and plays, and records after every step the hand with its
face-down cards starred, the row the same way, and the `wheel` pool's state
compared by its bits. Pareidolia, one and two Oops! All 6s, Chicot, and Amber
Acorn on rows of one, two, four with Chicot, and five, are cases of their own.
A wrong pool name, or a Fish that deals its opening hand face down, each
fail it at once.

How the policy plays against them -- deciding on a copy with the face-down
cards blanked -- is `rumbot`'s `rust/handcrafted/src/facedown.rs` and its ARCHITECTURE.md.

### Real recorded human games

`tools/gen_replay_fixture.py` drives the Python simulator through every
`external/jimbot-sim/recordings/*.json` -- 15 real human runs, 4,140 merged
actions, reaching ante 9 -- and writes one trace per recording into
`tests/fixtures/replay_<n>.txt`. `tests/replay_fixture.rs` rebuilds the same
`GameState` (seed/deck/stake, plus the recorded bankroll), applies the recorded
hand/joker arrange (`match_hand_order`, `match_joker_order`, a `sort_hand`
press) and then the recorded action, and compares every field after every step.
All 4,140 steps match. This is the distribution `flow_fixture` cannot reach:
a human opening specific packs, facing boss and finisher blinds, and buying the
jokers a scripted policy never chooses.

It caught two engine bugs the flow fixture never met:

* `GameState::_fill_shop` (game.rs) built the new slots in a local and swapped
  them in after the loop, so a *rerolled* shop's second draw could not see the
  first (`seen_centers` blanks a pool with what exists). A reroll drew
  `c_star, c_star` where the game had `c_star, c_heirophant`; the opening shop
  escaped only because `_open_shop` sets the empty shelf before filling it.
  Python empties `shop.slots` in place and appends each slot as it is made
  (game.py:3509).
* `GameState::_most_played_planet` (game.rs) used `.any()` over `HANDLIST`,
  which stops at the *first* hand with a play rather than the most played.
  Recording 16 played Pair nine times and Four of a Kind once, so Telescope
  forced Mars where the game forced Mercury. Python's `max` scans the whole of
  `HANDLIST` (game.py:3889).

Both are invisible until a field is compared that depends on them, which is the
argument for driving real recordings rather than a policy that shares the
simulator's own blind spots.

### Where the Python was wrong too: the order the game walks its hands

Every fixture here checks the Rust against the Python, so a rule the Python
got wrong passes all of them. To Do List was one. The game builds its pool of
hands by walking `pairs(G.GAME.hands)` and then indexes into it: To Do List's
hand when the card is made (card.lua:313) and at round end (card.lua:2977),
and each blind's Orbital Tag hand (UI_definitions.lua:1511). Both simulators
walked `HANDLIST` instead, because `hands.py` said the game's order could not
be reproduced: LuaJIT seeds its string hash per process. That was measured on
lupa's LuaJIT 2.1. The shipped `lua51.dll` is LuaJIT 2.0.5, whose hash is the
string's alone, so the game's order is the same in every process.
`hands::GAME_PAIRS_ORDER` is that order, read by running the `hands` literal
from game.lua:2001 through the game's own DLL over ctypes. The headless
engine's `pairs` patch (`headless_api.lua`) now walks the same list. It used to
walk `G.handlist`, so the headless replay agreed with the simulator by
construction.

It was found on the live game. JOKER189 (Blue Deck, stake 8) bought a To Do
List that named Three of a Kind in the game and Pair in the shadow. The policy
farmed Pairs for $4 the game never paid, and interest on the phantom dollars
widened the gap at every cash-out. The bridge does not refuse a buy the game
cannot afford, so the shadow shopped the game down to -$36.
`play_handcrafted_rs.py` now holds the game's money against the shadow's
before every decision and stops at the first difference that does not settle.
A `live` built with the old order stops at decision 47, $21 against $25.

The fix moved three per-step fixtures (FLOW0013, FLOW0025, FUZZ0007) and 187 of
the 640 sweep lines. All were regenerated from the patched Python with
balatro_bot's `tools/` generators, pointed at this tree's submodule with
`JIMBOT_SIM_SRC`. Before regenerating, check that the generators reproduce the
committed fixtures from the unpatched Python. On Windows that needs
`PYTHONUTF8=1` (Séance is otherwise written in cp1252) and the CRs stripped
afterwards (`write_text` writes CRLF). The sweep is 640 runs, about seven
minutes in one process: map `drive` + `sweep_line` over `SWEEP_RUNS` across
processes and it is two.

### The full observation under the real recordings

The thirteen fields above are a handful of the 42 top-level keys `state_dict`
returns (~1,900 leaves), and the observation layer was otherwise verified only
against nine hand-built cases. So every recorded step now also carries **one
digest per top-level key**. `tools/state_render.py` is the single canonical
renderer for both fixtures -- bools `i:`, ints `i:`, floats as the IEEE-754
bits, `None` as `n:`, and an empty list or dict as its own leaf -- and a
subtree's digest is FNV-1a-64 over its `path<TAB>value` leaves joined by
newlines. `src/state.rs` implements the same bytes, and its
unit test asserts the same three anchors `python tools/state_render.py` prints,
so a mismatch in the hash cannot be mistaken for a state divergence.
`tests/replay_fixture.rs` compares the digests per key after every step and
names the key, both digests and the `--dump` command on mismatch: 42 keys x
4,140 steps = **173,880 key-step comparisons**, all matching.

The picking `state_dict(game, selection)` takes is reconstructed, not recorded:
the simulator has no highlighted card, so the replay uses the action's own card
indices for a PLAY or DISCARD (what the agent would be holding) and the empty
selection otherwise. The generator emits it as its own column and Rust passes
the identical one, so a drift in either side's derivation is a failure rather
than a silent difference. The fixture header says so; `selected_hand`, the
`hand` flags and `selection_size` all move with it, so the reconstruction is
compared rather than assumed. No key needed the environment: all 42 are built
from `GameState` alone, so none is skipped.

### The preview values under the real recordings

The observation digests cover what the *state* is, not what the policy *sees*.
In every playing round `legal_actions()` offers a few hundred candidate subsets
and the choosing agent ranks them by `preview_score` (and `preview_money`,
`preview_outcome`, `preview_value`), which no fixture had ever checked the
*values* of: the flow fixture mirrors a policy that picks the argmax, so a
scoring error that does not change the winner slips through entirely. So every
recorded step now also carries **ten preview digests**, over every legal PLAY
and DISCARD action:

| kind | call | value |
|---|---|---|
| `scores` | `preview_score` (mode `"roll"`) | the score |
| `pessimistic` | `preview_score(mode="pessimistic")` | the score |
| `money` | `preview_money` | `[score, expected]` |
| `outcome` | `preview_outcome` | `[score, dollars, rolls]` |
| `value` | `preview_value` (mode `"roll"`) | `[score, dollars]` |

Each kind gets two digests over the same list of `{"<action>": value}` pairs,
laid out so `state_render.py` and `state.rs` render them identically: the
action's `repr` (which `Action`'s Rust `Display` matches byte for byte) is the
key, and a tuple value is a list so each part is its own leaf.
`<kind>_sorted` hashes the pairs sorted by the action rendering, so it is
ordering-independent -- a mismatch is a wrong *value*; `<kind>_order` hashes
them in `legal_actions()` order, so a mismatch while `_sorted` matches is a
wrong *order*, which matters because a policy breaks ties by position. Both are
reported, because that distinction is the point.

`--dump <recording> <step> <kind>` prints the same leaves in canonical
(action-sorted) order, so a digest mismatch becomes the exact differing action
in one command (the state-key `--dump` still works; a preview kind is one of
the five names above). `tests/replay_fixture.rs` recomputes all ten digests
after every step and reports recording, step, kind, both digests and the dump
command on mismatch.

Every preview is also a **read-only proof at scale**: the test reads the whole
observation (all 42 key digests) and the RNG pool signature before running the
previews and again after, and asserts they are byte-identical. A preview that
mutates the run is the worst bug here because it is invisible until a seed
diverges hours later, so it is checked at all 4,140 positions, not the handful
of hand-built cases the review path started with. The generator asserts the
same thing on the Python side, since it computes the observation before the
previews too.

The previews are fixtured as the Python computes them, which keeps
`blind.triggered` from the last real play: after a hand that set the boss off
every preview pays Matador's $8, The Arm and The Ox never set it, and a
refused hand previews $0 dollars. `GameState::preview_trigger` (false by
default, so every digest above is unchanged) makes `_preview` set the trigger
for the play it scores instead; nothing in the simulator sets it, the policy
does under `fix_preview_trigger` (`tests/port_b.rs`,
`test_a_preview_*`).

Mode `"expected"` is deliberately not fixtured: `preview_value`'s expected
dollars is a Python `float`, while the Rust returns the mean rounded to an
`i64`, so comparing it would be a return-type artefact rather than an engine
divergence. `"roll"` and `"pessimistic"`, the two modes `_preview_mode` picks
between for a score, are both covered.

### Random legal actions at a one-chip target

`tools/gen_fuzz_fixture.py` + `tests/fuzz_fixture.rs` are a different kind of
fixture. Every blind's target is forced to 1 chip, so any play beats the blind
and runs progress deep and fast; a seeded `random.Random` then picks uniformly
from `legal_actions()` at every step. The actions are random rather than the
flow policy's or a human's, so they reach shops, packs, boss blinds, antes and
the finisher through states neither the 15 recordings nor the flow seeds ever
did. 12 seeds, 1,547 steps, deepest ante 11, across Red/Blue/Yellow/Plasma/
Erratic/Ghost/Green/Painted/Zodiac/Black decks and stakes 1..8 (so stickers and
the reduced starting discards are in play).

What makes it a rules test is that every step digests the **legal action list
itself**, not just the outcome. `legal_actions()` is the whole interface to the
rules -- Death takes exactly two cards, an eternal joker cannot be sold, a boss
cannot be skipped, a full row cannot buy a sixth -- so a digest over it checks
the whole action mask, which no fixture here had ever done. Two digests per
step, the same ordered/sorted pair the previews use: `legal_sorted` catches a
*missing or extra* action, `legal_order` a wrong *order*. Each step also carries
all 42 per-key `state_dict` digests and the raw RNG pool signature. A mismatch
reports seed, step, kind, both digests and the `--dump <SEED> <STEP> [<KEY>]`
command; `--dump` with no key prints the legal actions in canonical order with
the chosen one marked, with a key prints that key's leaves.

It found one engine bug, fixed here: a joker with a `round_money` (Delayed
Gratification) **sold on the cash-out screen** still pays its row, because
Python's `_beat_blind` snapshots the joker *instances* (`game.py:3261`) and
`_cash_out` runs them (`game.py:3324`). Rust kept uids and re-resolved them
against `self.jokers` at cash-out, so a sold joker's row vanished -- FUZZ0009
step 163, $50 against $44. `dollar_rows` now holds the `JokerRef`s.

One divergence is **recorded, not fixed**, because it is a fixed-width boundary
rather than a dropped rule. `state_dict`'s `blinds` row reports
`int(ante_base_chips(...) * mult * ante_scaling)`; Python's int is unbounded
(86 * 10^19 at ante 16), while `ante_base_chips` returns a saturating `i64`
(`i64::MAX` from ante 16 up). FUZZ0001 step 347 (ante 16) and FUZZ0002 step 312
diverge on exactly that key. Closing it needs arbitrary-precision integers
throughout -- `chips_scored` is an i64 with the same ceiling -- so the committed
fixture is capped below ante 16 (which the fixture's size buys anyway) and the
boundary is spelled out on `ante_base_chips`. A throwaway 500-step hunt with
the `blinds` key set aside replayed every seed to ante 24 with no other
divergence, legal-action digests included.
